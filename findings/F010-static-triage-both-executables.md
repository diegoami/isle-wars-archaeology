# F010 Both executables can be read with open tools: Isle Wars Pro is a Director 7.0 projector whose 213 Lingo scripts decompile with their handler names, and its SaveDefaults handler writes `Isledft.dat` as eight comma-ended fields in the order F003 observed; DOS Isle Wars is a compiled Microsoft BASIC program packed twice (PKLITE 1.15 over Microsoft LINK's EXEPACK), and the routine at `1000:9b33` of its unpacked image writes `ISLEWAR.SAV` in the order of lines F009 found

- **Status**: proposed
- **Question**: Can both executables be unpacked, loaded and read with open tools (U32, static first), what do the tools recover, and does a static reading agree with what the runs of F003, F007 and F009 observed? (T26, E008.) Feasibility probes: the code that writes `ISLEWAR.SAV` (DOS) and the handler that writes `Isledft.dat` (Pro).
- **Tests claims**: R001 to R007 (Pro, `Isledft.dat` and `Islepro.skr`; static agreement and, for R004 and R007, a static reading of what the runs left unknown). R012, R014 and R017 to R023 (DOS, `ISLEWAR.DFT` after Load and `ISLEWAR.SAV`, F007; and F009's layout, proposed on PR #75): static agreement with the order of lines, and, for R021 and R014, a static reading of where the values come from and which action rewrites the file. No game rule is claimed.
- **Experiment and runs**: E008 (static only; no run). Its measurements are in `experiments/E008-static-triage/measurements/`.
- **Artifact**: set `iwp-2.0-996e86c5` for Pro (`Islepro.exe`, sha256 `c4d7a248646454adeb48232e3ac7b3d2c0f08b290051a79d6fe6e47bb76b594e`, 7150739 bytes, the same file in all three registered Pro sets); set `iw-dos-3.1-30121376` for DOS (`ISLEWAR.EXE`, sha256 `88e934bb4fa0b074a926d53765bbca251cb38395da50337276aac7d08a5cde45`, 83580 bytes; and `ISLEWAR.OV6`, sha256 `680a39e95fd37a18b0e9519bda2c758395729671f067084bdbdbef58eb211fcf`, 58688 bytes, the set's second executable). Variant none.
- **Max intervention**: I0 (the originals were only read, in place; every derived file is a new file in a folder outside every checkout)
- **Tier reached**: V0 (static)
- **Confidence**: Pro, the layout, the counts and the probe: high, because the counts come from the tool's own chunk reading and the probe's field order is read directly from a short handler (the determinism of the output is for the re-run of Done-when 2 to show). It rests on one decompiler (ProjectorRays 0.2.0) and no run corroborates a *behaviour* (the offsets agree with F003, which is a corroboration of the file layout only). DOS: the two packers, high (two readings agree: the header read here and Deark's own analysis, and the unpacked image passes every check of a plain executable). The compiler, Microsoft compiled BASIC: about 90%; which version (QuickBASIC 4.x or BASIC PDS 7.x): not established. The save probe: about 85% that the routine at `1000:9b33` is the one the Save button runs (it is the one place that opens `ISLEWAR.SAV` for writing, and what it writes has F009's shape line for line); the code was read by a person from Ghidra's listing, and no run was made to tie the routine to the button.

## Answer

### Pro

- **`Islepro.exe` is a Director projector for Windows with one embedded Director movie.** A PE image of 162816 bytes (ends at file offset 0x27c00) is followed by a projector header `PJ00`, which points at a Director container (`APPL`) at offset 0x1b8ce8. The container's chunk map has 23 chunks: itself, an initial map, the map, a list, a dictionary and 18 embedded files. Seventeen are not Director files (their first bytes are neither `MZ` nor `XFIR`; not identified here) and one is the movie, 4522178 bytes at offset 0x281bce, codec `MV93`. `static:experiments/E008-static-triage/measurements/iwp-extract-pro-r1.json`, field `layout` and `embedded_files`, binary sha256 above.
- **ProjectorRays 0.2.0 reads the movie and reports Director 7.0.** It reads 1504 chunks, 650 cast members (389 bitmaps, 121 scripts, 57 text, 19 sounds, 2 shapes, and 62 of types 14 and 15, which the tool does not name) and writes the movie back as a 4687621-byte `.dir`. The projector's own map says version field 1406; the tool maps the movie's own config value to 7.0. `static:experiments/E008-static-triage/measurements/iwp-extract-pro-r1.json`, field `movies[0]`.
- **213 scripts and 230 handlers decompile, names intact.** 34 movie scripts, 87 behaviour scripts and 92 cast-member scripts, 7358 lines of decompiled text (counted, not kept here). ProjectorRays marks what it cannot decompile in its output (the word `ERROR`, and an opcode named `unk` with two hex digits in a bytecode listing); counted over the 213 scripts and 213 bytecode listings the record lists, each checked by its sha256, there are none (`static:experiments/E008-static-triage/measurements/iwp-markers-pro-r1.json`, `tools/static/iwp_markers.py`). Handler names survive (`SaveDefaults`, `Getdefaults`, `MakeComputerMove`, `Computerattack`, `RollDice`, `CheckCardMatch` and so on; the table of all of them is in the record), and so do global and local variable names. The script context lists 274 scripts; the 61 that no cast member points at are not written by the tool and were not read. `static:experiments/E008-static-triage/measurements/iwp-extract-pro-r1.json`, fields `scripts`, `script_count`, `handler_count`, `scripts_without_a_cast_member`.
- **Probe: `SaveDefaults` (script `MovieScript 458 - getdefaults`, cast member 458) writes `xtras\Isledft.dat`.** It builds one string of eight items, each followed by a comma: first the four opponent flags (`opp`, `1` or `0` each), then the speed, the frequency, the starting armies and the strength, in that order, then writes the string with the file Xtra. The reader `Getdefaults` (same script) takes items 1 to 4 as the four flags, item 5 as speed, 6 as frequency, 7 as starting armies and 8 as strength, and falls back to 2, 2, 3 and 2 for a zero. The button script `CastScript 602 - SAVEDEFAULT2` calls `SaveDefaults` on mouse down. `static:decompile`, `Islepro.exe` sha256 above, `MovieScript 458` handlers `Getdefaults` and `SaveDefaults`, `CastScript 602`.
- **The static reading agrees with F003 and answers two of its open rows.** See the table in Observations: eight comma-ended items (R001), speed at offset 8 (R002), level at offset 14 (R003), and the six items F003 never saw change, whose meanings the reader gives (R004: flags at offsets 0, 2, 4 and 6, frequency at offset 10, starting armies at offset 12). For the scoreboard file `Islepro.skr`, the writer `writescores` adds the won and lost counts to a pair of items chosen by the level (items 5 and 6 at level 1, 3 and 4 at level 2, 1 and 2 at level 3), then writes seven items each followed by a comma, after adding the constant 94 (0x5e) to the code of every character (`CIPHER`, `MovieScript 480 - checkupg`). That agrees with R005 and R006, and it answers R007's untested idea (offset 2 is the lost count of level 3, which F003 calls EASY). `static:decompile`, `MovieScript 455`, `MovieScript 480`.
- **The start handler explains the shipped files.** On every start `startMovie` (`MovieScript 1`) creates each of `Islepro.dat`, `Islepro.skr` and `Isledft.dat` that is missing; for `Isledft.dat` it writes the eight items without the last comma (15 bytes, the shipped size, R001), for `Islepro.skr` seven items of zero (13 bytes, the shipped size). `SaveDefaults` and `writescores` append a comma after the last item, which is the 16 and 14 bytes F003 saw after a write. `static:decompile`, `MovieScript 1`, `MovieScript 455`, `MovieScript 458`.
- **Why the locked controls never moved.** `Getdefaults` resets the opponent flags, the frequency and the starting armies to their defaults when the global `UPG` is 0. F003 found these controls locked in the unregistered build and no run could change those items. That is the reason the six items stayed unchanged, read from code and not shown by a run. `static:decompile`, `MovieScript 458`, handler `Getdefaults`, last block.

### DOS

- **`ISLEWAR.EXE` is packed twice: PKLITE 1.15 (extra and large settings) outside, Microsoft LINK's EXEPACK inside.** The MZ header carries the PKLITE text at offset 30 and the version bytes `0f 31` at offsets 28 and 29, version 1.15 with the extra-compression and large flags (`dos-identify-r1.json`). Deark 1.7.3's PKLITE module reads the same (`1.15/l/e`, extra 1, large 1) and decompresses 82770 bytes to 146422; its output, 146454 bytes, sha256 `840049beb52a545ef75d5005f3ef760621d45dcc03879c777e507a177fe1c23e`, has no relocation of its own and starts at EXEPACK's decoder, whose error text it holds. Deark's EXEPACK module recognises that decoder as the 290-byte kind it names "common290 (LINK 5.60/etc.)", restores 2930 relocations, and writes the unpacked image: **159120 bytes, sha256 `4dac918a532fa439ad98cd519a1daf43a51067639e1b80855d2b69acab4374d3`**. `static:experiments/E008-static-triage/measurements/dos-unpack-exe-r2.json` (and `-r1.json`, the same hashes from an earlier run), binary sha256 above.
- **The unpacked image is a plain DOS executable.** Header 11760 bytes, load module 147360 bytes, image length equal to the file's; all 2930 relocations point inside the load module and name 22 segments; entry point `1d78:0b4a` inside the module; neither packer's text is left (`dos-unpack-exe-r2.json`, field `unpacked`). The two runs of the unpack, r1 and r2, gave the same three hashes.
- **`ISLEWAR.OV6` is a second executable, packed the same way.** PKLITE 1.15 with the large flag only (`1.15/l`), then EXEPACK of the same kind; unpacked, 92736 bytes, sha256 `1c6f8fb1c9eceb190fc40856110dd6e001a081aa9ea56ad1cbcbf9d99820b2de`, 1002 relocations, entry `0fd8:0624`, plausible on every check (`dos-unpack-ov6-r2.json`). It names neither `ISLEWAR.SAV` nor `ISLEWAR.DFT` (`dos-probe-ov6-r1.json`); what runs it was not read.
- **The compiler is Microsoft's compiled BASIC, with its stand-alone run-time library linked in (about 90%).** The evidence, each in `dos-probe-exe-r1.json` unless named: (1) all 8 of the run-time error texts chosen here as markers of Microsoft BASIC's library (texts no C or Pascal library prints, such as the error for a RESUME with no error) are in the image, and all 3 markers of Microsoft C's library (the `R6000`-series texts that library shares); none of the 10 markers of Borland's Pascal and C libraries or of other BASIC compilers is; (2) those texts are inside the executable, and the set has no separate run-time module (`artifacts/known.json`, set `iw-dos-3.1-30121376`), so the library is linked in; (3) each of the four file names the probe searched for is stored, where it stands alone, as a four-byte descriptor (a length, then the offset of the text) immediately before its text, and the four descriptors give the same data-segment base, `0x213b0` (the two other places that hold a name, inside a longer message, have no descriptor; no other string constant was tested): the descriptor layout of Microsoft's BASIC; (4) the linker's EXEPACK (Deark, above); (5) F007 found the files written as numbers with a space before and after (` 1 `), which is how BASIC's `PRINT #` writes a number. `ISLEWAR.OV6` holds the same 8 BASIC markers and 2 of the 3 C ones (`dos-probe-ov6-r1.json`). Which compiler version: not established. The wording of one error text (number 73) leans to QuickBASIC 4.x over BASIC PDS 7.x, about 60%, from memory of the two products' texts and not checked against a reference.
- **Ghidra 12.1.4 imports the unpacked image as 16-bit real mode and exits 0: 361 functions, 7891 instructions, 24 memory blocks, in 9.4 s.** The first code block is `1000:0000`, 65504 bytes. Auto-analysis reaches a small part of the code: compiled BASIC is entered from its library's start-up through tables Ghidra does not follow, so the probe had Ghidra disassemble from addresses found by the descriptors (`--range`). A second import with the probe's ranges gave the same 361 functions and 7891 instructions (they are counted before the ranges are disassembled). The unpacked `ISLEWAR.OV6`: 509 functions, 18990 instructions, 21 blocks, 11.4 s. `static:experiments/E008-static-triage/measurements/ghidra-dos-exe-r1.json`, `ghidra-dos-exe-r2.json`, `ghidra-dos-ov6-r1.json`. The packed file had given 1 function (`ghidra-dos-packed-r1.json`).
- **Probe: the descriptor of `ISLEWAR.SAV` (data-segment offset `0x1968`) is pushed at three places, `1000:964d`, `1000:9743` and `1000:9b89`** (`dos-probe-exe-r1.json`). Read by a person in Ghidra's listings (`ghidra-dos-exe-r2.json`, ranges `1000:964d-1000:9738`, 76 instructions; `1000:9739-1000:9b32`, 381; `1000:9b33-1000:9d5f`, 194; the listings stay in the machine-local folder):
  - **`1000:9b89` is in the writer, the routine that begins at `1000:9b33`** (after a return at `1000:9b32`). It first opens `ISLEWAR.DFT` (its descriptor `0x1450`, pushed at `1000:9b38`) for reading and reads three values into the data-segment words `0x079c`, `0x07a4` and `0x003a`, and closes it; then it opens `ISLEWAR.SAV` with the mode value that the reading routine does not use, and writes, each as its own statement on channel 1: the word `0x0370`; a loop from 1 to that word, one line per element of a table; four lines of one value each, `0x079c`, `0x07a4`, `0x003a`, `0x0030`; a loop of 46 (the bound compared at `1000:9c93`), each line a value a library routine returns from the country's two coordinates in two 46-entry tables; a loop of 46 (`1000:9cc5`), one table element per line; one line of the four words `0x0032` to `0x0038` with a one-character string constant (a comma) between them; one line of four string variables (`0x003c`, `0x0040`, `0x0044`, `0x0048`) with the same separator; and it closes the file at `1000:9d5f`.
  - **`1000:9743` is in the reader** (`1000:9739` to `1000:9b32`), which opens the file with mode value 1 (the writer's is 2) and reads the same sequence, value for value, into the words and tables the writer wrote from, but for two: the level line goes into `0x0e8c`, and each owner into a temporary word that is then given to library routines with the country's coordinates. It then writes `ISLEWAR.DFT` (pushed at `1000:9ad8`) as three lines from `0x0e8c`, `0x07a4` and `0x003a`.
  - **`1000:964d` passes the name to a far routine with a result word (`0x04d6`) that is tested next.** Probably the test for a saved game (F007's `NO SAVED GAME FOUND`), about 60%; not read further.
- **The writer's order is F009's layout, line for line** (the table in Observations): N, the N centres, the level and the starting armies, Speed, Sound, 46 owners, 46 armies, the card counts on one comma-separated line, the hands on the last. Two things the runs could not show come out of the reading: the level and armies lines are written from the values just read back from `ISLEWAR.DFT` (R021 found the save's two values equal to the file's), and Load rewrites `ISLEWAR.DFT` as three lines (R014's three lines ` 1 `, ` 1 `, ` 2 `, whose writer F007 did not isolate; F009 E007-r0034 showed it by a crafted save). The owner value is what a library routine returns for a point of the country; that this routine reads a screen pixel's colour, which would make the codes 9, 4, 2 and 8 colour numbers, is an inference, about 70%, not a reading.

## Method

- **Artifact and tools.** The two executables were read in place, after each was hashed and matched to its registered sha256 (`tools/static/static_common.py`, `original`). Tools and their identities are in `docs/environment.md`, "Static analysis tools", and `setup/static/tools.json`: ProjectorRays 0.2.0 (commit 8a3d3b4, built from source, binary sha256 `d1c2235bd5f32f4a268a2cd09d2260e143b8caf51124e0da8d9f54fd113c0ea3`), Ghidra 12.1.4 PUBLIC with JDK Temurin 21.0.12.1+1-LTS, and the scripts under `tools/static/`. The version word of PKLITE is read as Entropymine's notes describe it.
- **Pro.** `tools/static/iwp_extract.py` reads the PE image end, the `PJ00` header and the container's chunk map, carves the movie, and gives ProjectorRays a work copy that keeps the movie at its original file offset (the first 44 bytes at offset 0, the movie again at its offset, zeros between): the movie's internal offsets are those of the executable, and ProjectorRays reads them as offsets in the file it is given. It then runs `decompile --dump-scripts -v` and a second run with `--dump-json`, and counts. `--probe NAME` lists the handlers that mention a file name and whether each reads or writes a file. The probe's field order was read from the decompiled handlers in the machine-local folder; nothing of it is kept here. Run `pro-r1`; the record is `iwp-extract-pro-r1.json`.
- **DOS.** `tools/static/dos_identify.py` reads the MZ header and the PKLITE version word in place (`dos-identify-r1.json`). `tools/static/ghidra_import.py` imports a file with `analyzeHeadless -processor "x86:LE:16:Real Mode" -cspec default` and the post-script `tools/static/ghidra/T26Report.java`: first the packed original in place (`ghidra-dos-packed-r1.json`). `tools/static/dos_unpack.py` then runs Deark 1.7.3 (sha256 `70c93ae2755a4682bf249b91c76e088d47225e1bda867916f3a3dae5d4bb8e23`) twice, `-m pklite` on the original read in place and `-m exepack` on its output, into a new folder of the machine-local static folder, hashes each output, checks the last as a plain executable and hashes the original again (runs `exe-r1`, `exe-r2`, `ov6-r1`, `ov6-r2`). `tools/static/dos_probe.py` reads the unpacked image (by its sha256) for the markers of a run-time library and for the descriptors of four file names and the places that push them (`dos-probe-exe-r1.json`, `dos-probe-ov6-r1.json`). Ghidra imported the unpacked image (`ghidra-dos-exe-r1.json`), and again with `--range` for the three places that push `ISLEWAR.SAV`'s descriptor, the first two from the address after a return to the next return, the third from the address after a return to the call that closes the file, which wrote Ghidra's listings into the machine-local folder (`ghidra-dos-exe-r2.json`); the order of the writer's statements was read from those listings by a person, and is described here in our words. While locating the places, the implementer also looked at the same bytes with GNU objdump 2.42 (`-m i8086`; the system's binutils package `binutils-x86-64-linux-gnu` 2.42-4ubuntu2.8, binary sha256 `d0041e7511460b9ebfd95ce4f9d93c7ffea398ffc1cb2c316a220dd8e533db3d`, recorded in `docs/environment.md` and under `terminal_only` in `setup/static/tools.json`), in the terminal only: nothing it printed was kept or tracked, no script runs it, and the probe's addresses and reading are Ghidra's. The PKLITE version word is read as Entropymine's notes describe it, and Deark's reading agrees.
- **What is tracked.** Hashes, sizes, counts, addresses and identifier names. The carved movie, the work copy, the rebuilt `.dir`, the decompiled scripts, the two unpacked stages of each DOS executable, Ghidra's projects and listings stay in a folder outside every checkout (rule 18). Every file of each run folder, the tools' own files included, is listed by sha256 and size: in the run's record (`derived_files`), and, for the folders made before the scripts did that, in `inventory-r3-<folder>.json`. `tools/static/check_derived_hashes.py` checks that no tracked file is one of them, whatever its name.

The reader at `1000:9739` reads the same sequence in the same order, and then writes `ISLEWAR.DFT` as three separate lines from `0x0e8c` (where it put the level line), `0x07a4` and `0x003a` (`1000:9ad8` to `1000:9b28`): R014's three lines after Load.

## Inferences

- The projector can be read with open tools and the Lingo comes back as readable source with names: from the counts in `iwp-extract-pro-r1.json` and the zero count of ProjectorRays' error markers in `iwp-markers-pro-r1.json`. That the *behaviour* the source describes is what the game does is not shown by this reading; F003's offsets agreeing is the one corroboration, and it covers a file layout.
- The offsets and order agree with F003 on every row F003 had (R001 to R003, R005, R006), from the table above and the `writescores` reading. Two independent methods (runs, and a static reading) now name offsets 8 and 14 the same, which is the independence `vocabulary/basis.md` asks for before `corroborated`.
- The six items that no run could move are the opponent flags, the frequency and the starting armies, from the reader's own naming and its reset when `UPG` is 0. That `UPG` is 0 in the unregistered build is a reading of the start handler and was not observed.
- A static answer to R007's untested idea (offset 2 is a lost count) exists in the writer's pairing of items with levels; no run produced an Easy loss, so this is the one place a run is still owed, if the claim is to be promoted.
- DOS: the executable can be unpacked and loaded with open tools, and the order of the fields the game writes can be read from it: the routine at `1000:9b33` writes F009's lines in F009's order, and the reader at `1000:9739` reads them back in the same order (the table above). A run made the file; a static reading now names the same lines in the same order, two independent methods for the layout of R017 to R023. That the routine is the one the Save button runs is not shown by this reading (about 85%, see Confidence).
- DOS: the save takes its level and starting-armies lines from `ISLEWAR.DFT` as it is when Save is pressed, and Load rewrites `ISLEWAR.DFT` from the save, three lines; this explains R021's equality and R014's file, as a reading of the code (no run tested the order of events).
- DOS: the cost of reading the DOS game is in the reading, not in the tools. No names survive, auto-analysis reaches a fraction of the code, and each routine has to be found from a file name, a text or a data word, as here. Pro's Lingo, with its names, is far cheaper to read: the estimates of the area table rest on that difference.

## Alternatives considered

- **The decompiler invented the handler order or the names.** Not excluded by a second decompiler (only ProjectorRays 0.2.0 was used). Made unlikely by the names being the movie's own name table (`Lnam`), by none of the 213 scripts holding one of ProjectorRays' error markers (`iwp-markers-pro-r1.json`), and by the order of items agreeing with F003 at offsets 8 and 14.
- **The scripts that no cast member points at (61) hold the real write.** The probe's handler is in a script a cast member points at, and its output agrees with the runs, so excluded for this file; for any other question the 61 are unread.
- **The agreement with F003 is by construction (the same defaults).** Excluded for offsets 8 and 14 (the runs changed them and the reader says which item they are) and not excluded for the default values, which both sources could take from the same shipped file.
- **For DOS, the PKLITE reading is a coincidence of bytes.** Excluded: Deark's PKLITE module recognised the same version and flags from the decompressor's code and returned an image that is a plain executable once its second layer is removed.
- **The unpacked image is not what the packed one runs (an unpacker's error).** Not excluded by a second unpacker. Made unlikely by the checks of `mz_facts` (every relocation and the entry point inside the load module, image length equal to the file's), by the strings and descriptors falling into one data segment with one base, and by the writer's structure matching F009's file line for line, which a corrupted image would not give.
- **The writer is another routine than Save's, such as an autosave or a debug path.** Not excluded by a run. Made unlikely by there being one writer of `ISLEWAR.SAV` (one push of its descriptor followed by an open with the writing mode) and by its output having the shape of every natural save of E005 and E007.
- **Another compiler that uses Microsoft's BASIC run-time texts.** Not excluded; no such compiler is known to the implementer. The descriptor layout, the EXEPACK of Microsoft's linker and the number format add to the run-time texts.

## What this does not establish

- **Most of the DOS game's code.** Three routines were read, those that use `ISLEWAR.SAV`; nothing else of the 147360-byte load module was read, and `ISLEWAR.OV6` was unpacked and imported but not read. Which BASIC compiler version, the meaning of the library routines the writer calls (named here by what they are given and return), and the meaning of any data word beyond what F009 gives its line are not established.
- **That `1000:9b33` is what the Save button runs**, and what calls `1000:964d`. No caller was traced.
- **Any game rule.** The area estimates are estimates. No handler was read to learn a rule, and none is claimed.
- **The registered builds, the other Pro sets, other versions**, and what registration unlocks beyond what the unregistered build's code gates.
- **The 61 scripts without a cast member, the 17 other embedded files, the cast members' pictures and text, the score (`VWSC`) and the sounds.** Counted or ignored, never read.
- **That the decompiled Lingo is faithful in every handler.** One decompiler, no corroborating run for any behaviour.
- **Ghidra's and the JDK's archives.** Both were installed by the owner; their files are identified by hash, and the archives' published checksums were not compared (Ghidra's is recorded as published). Deark was built from its tagged source by the main session; its binary is identified by hash.
