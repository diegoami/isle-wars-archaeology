**In one paragraph.** The game's setup is one screen, reached from the bottom menu's options entry, that shows and sets six things: the four seats (human or computer each), the starting-armies value (five entries), the strength level (three entries), the event frequency (four entries), the animation speed (three entries) and sound on/off; a save button writes the five settable values to a defaults file, and a play button starts the game. The unregistered build locks three of the six (seats, armies, frequency) behind the registration check and pins their values (one human at seat 1, armies 3, frequency normal) at every start, so the effective setup is fixed furniture around one live dial (the level) and one cosmetic one (speed), plus sound. The game keeps exactly three files in its data folder — the defaults file (eight comma-separated numbers, plaintext), the scores file (seven numbers behind a fixed character-shift cipher), and the registration file (the entered name, its scramble check) — creates each when missing, and no handler in the corpus opens anything else: there is no save, no load, no export, no import, and no menu entry for any of them. None of the three files carries a version or format number; the defaults reader replaces only five specific bad cases (a seat table with no human, a zero speed, a zero frequency, a zero armies value, and a strength that is zero or above ten) with the standard defaults, while other out-of-range values survive it; the scores reader validates nothing and converts the supplied items into its zero-initialised list; and only the registration check can reject (its scramble re-derivation). What the readers make of any other malformed content is a runtime outcome this reading does not establish (unknown). Every random value the game ever draws — deal, armies, centres, first seat, dice, events, cards, the computer's every choice — comes out of the one Director random function, in 91 call sites across 17 scripts, and no script sets, reads or stores a seed: the Lingo cannot reproduce or anticipate the stream, and the game cannot replay a game because it cannot even hold one.

### The options screen

- **As read (about 90%).** The setup is one screen. Each control has a click handler, and each handler's click arithmetic covers exactly its sprite block: the armies handler takes clicks on sprites 165 to 169 and sets one of the five values 1, 3, 5, 7, 10 (`BehaviorScript 496 startingnumarmybehavior` / `mouseDown()`); the strength handler takes 174 to 176 and sets 1 (hard), 2 (normal) or 3 (easy) (`BehaviorScript 498 STRENGTHbehavior` / `mouseDown()`); the frequency handler takes 177 to 180 and sets 1 (more), 2 (normal), 3 (less) or 4 (never) (`BehaviorScript 499 FREQbehavior` / `mouseDown()`); the speed handler takes 181 to 183 and sets 1 (fast), 2 (normal) or 3 (slow) (`BehaviorScript 500 SPEEDbehavior` / `mouseDown()`); the two seat toggles take 170 to 173 and flip that seat's human/computer value (`CastScript 568 HumanH` / `mouseDown()`; `CastScript 569 ComputerC` / `mouseDown()`); and the two ear icons flip the sound global (`CastScript 591 ear1` / `mouseUp()` sets sound off, `CastScript 592 ear2` / `mouseUp()` sets sound on). The sprite span is fully accounted for, so on this screen there are exactly six controls. The screen's remaining buttons are its save button, which shows a saved notice and writes the defaults file (`CastScript 602 SAVEDEFAULT2` / `mouseDown()`), its play button, which releases the option sprites and starts the game (`CastScript 604 PGAME2` / `mouseDown()`), and its return buttons, which step back, one of them clearing the option sprites first and one sibling's click handler being empty (`CastScript 606 RETURN5` / `mouseDown()`; `CastScript 607 RETURN6` / `mouseDown()`; `CastScript 605 RETURN4` / `mouseUp()`).
- **Defaults.** Three places agree on one default set, and the unregistered forcing pins part of it at every start (Q-SET-02): when the defaults file is missing, startup writes the eight numbers seats 1,0,0,0 (one human at seat 1, three computers), speed 2, frequency 2, starting armies 3, strength 2 (`MovieScript 1 Startmovie` / `startMovie()`); the defaults reader pre-sets the same five values before it opens the file, but every item is then overwritten by the value() of the file's item in that position, so the pre-sets are not an independent fallback for every malformed or short file (`MovieScript 458 getdefaults` / `Getdefaults()`); and its validation replaces exactly five bad cases after reading — a seat table with no human entry, a strength of 0 or above 10, a frequency of 0, an armies value of 0 and a speed of 0 — with the standard values, and range-checks nothing else (same handler). The sound toggle is the exception: it is not in the defaults file (the writer emits exactly the eight numbers above, `MovieScript 458 getdefaults` / `SaveDefaults()`) and nothing initialises it, so its start state is a runtime question; the display frame draws the sound-on icon when the value reads 0 (`BehaviorScript 457` / `exitFrame()`).

No rule-variant toggles exist beyond the event frequency. No player-count entry exists — the seat count is the four fixed toggles. No objective, no turn limit, no scenario choice. The speed setting's reach is presentation only: outside its own button, the display frames and the defaults handler, the census finds it read only by five of the eight delay helpers (each waits a number of ticks that is a small multiple of the value) and by two animation-repeat loops in the computer's placement handler; the other three helpers use fixed waits (`MovieScript 1 Startmovie` / `Count15()`, `count10()`, `count30()`, `count60()`, `count5()` are the five speed-scaled waits; `count1()` and `count2()` wait one tick and `count3()` waits three, none reading the value; `MovieScript 333 ComputerPlaceArmies` / `computerplacearmies()`; `experiments/E017-pro-setup-reading/measurements/searches-r2.json`, the speed census). ### The registration gates

#### Q-SET-02 Which features are restricted or absent in the unregistered release?

- **As read (the gates about 90%; the list's completeness about 85%).** The startup check reads the registration file and sets the flag that every gate tests (`MovieScript 480 checkupg` / `CHECKUPG()`): it takes the file's items (the entered name, the code, the stored scramble), re-derives the scramble — each character of the name shifted by its position plus a fixed offset — and sets the flag only when the derivation matches and the code equals a fixed literal; then it shows the registration line, naming the owner or saying the version is unregistered. In this build the file does not pass, so the flag is 0, and the code shows these gates:
  - **The seat toggles are locked.** Both refuse the click when the flag is 0, with a notice that multiple human players need the registered version (`CastScript 568 HumanH` / `mouseDown()`; `CastScript 569 ComputerC` / `mouseDown()`).
  - **The starting-armies option is locked**, same refusal shape, with a notice that the option needs the registered version (`BehaviorScript 496 startingnumarmybehavior` / `mouseDown()`).
  - **The event-frequency option is locked**, same shape (`BehaviorScript 499 FREQbehavior` / `mouseDown()`).
  - **The defaults forcing runs at every read**: when the flag is 0, the defaults handler replaces the seat table with one human at seat 1, the frequency with 2 and the armies value with 3, after the file's values are loaded and validated — so no file-supplied value for those three survives in this build (`MovieScript 458 getdefaults` / `Getdefaults()`). The strength and speed values are not forced.
  - **The scores record is capped.** When the flag is 0 and the six score slots sum above 50, the end-of-game screen skips writing the scores file and shows a notice that the unregistered version saves no more scores (`BehaviorScript 470` / `exitFrame()`, the only caller of the writer, found by search); the scores screen shows the same notice (`BehaviorScript 473` / `exitFrame()`).
  - **The quit and exit screens differ by flag**: the quit and exit buttons go to one of two screens each (`CastScript 355 quit2` / `mouseDown()`; `CastScript 666 exit2` / `mouseUp()`).
  - **The registration entry exists in this build**: the unregistered game reaches a screen where a name and a code are typed; the entry handler scrambles both and re-runs the check, going to a pass or fail frame (`MovieScript 494 Getusernames` / `GETUSERNAME()`, `GETCODENAME1()`). The entry is reached through a key watcher that a frame arms only when the flag is 0: enough presses of the two trigger keys open the entry screen (`BehaviorScript 510` / `exitFrame()`; `MovieScript 549 checkfor` / `CHECKFOR()`). Nothing here says what a passing code unlocks beyond the gates above.
  - **A startup anti-tamper check that never reaches the checker**: at startup the game scans its own folder for a file named from a fixed three-part string (Director's Lingo-initialisation name), and on a match assigns 100 to a variable of the same name as the registration flag (`MovieScript 1 Startmovie` / `startMovie()`). That assignment is to a handler-local variable — the startup handler does not declare the flag global, and the bytecode writes a local — while the checker tests the global flag and quits when it is 100 (`MovieScript 480 checkupg` / `CHECKUPG()`). So the file's presence does not reach the quit: the global flag is cleared and then re-derived from the registration file, and the apparent anti-tamper quit is inert in this build. The quit's shape (a quit when that file exists) is what the code appears to intend; its effect is not what it appears.
  - **A mid-game lock that only the registered build can meet**: the seat toggles and the frequency option also refuse clicks once a game has started, a gate on the game-started flag (set from the first turn frame, `BehaviorScript 461` / `exitFrame()`; cleared by the new-game button and the options entry, `CastScript 347 newgame2` / `mouseUp()`; `BehaviorScript 474` / `exitFrame()`). In this build the registration gate fires first, so the mid-game gate is reachable only registered — stated as read, not analysed (rule 19).
- **What the gates lock, in sum**: multiple humans, the armies value, the event frequency, unlimited score-keeping, and the shareware screens. Every one of these is a gate the code shows; what registration unlocks beyond them — any rule change, any extra content — is nowhere in this build and stays `unknown` (rule 19). The directions' claim that registration controls the starting armies, the disaster frequency and the colour matches the code's gates (knowledge-map, Pro setup row). Two smaller flag-keyed behaviours complete the census: the title screen shows a registration line of its own and swaps a label sprite by flag (`BehaviorScript 450` / `exitFrame()`), and the scores screen's reset button draws its hover images only when the flag reads registered (`BehaviorScript 475` / `exitFrame()`).

## Inferences

- **The unregistered game is one live dial.** With seats, armies and frequency forced and locked, the only setup decision a player of this build makes is the level (and speed, which changes no rule, and sound). Malpaco's setup screen should not assume more than this build shows — seats, armies and frequency are fixed furniture and only the level, speed and sound are live controls; what registration makes live stays `unknown` (rule 19). From Q-SET-01, Q-SET-02.
- **Everything a file holds is out-of-game metadata.** Options, a win/loss tally, a registration string: no position, no seed, no replay data exists anywhere in the build's persistence. Malpaco's scenario+seed design (the statements this research feeds) is therefore not a simplification of Pro — it is a capability Pro never had. From Q-SET-05, Q-SET-06, Q-RND-01.
- **The stream's order-dependence is a faithful-reimplementation hazard.** Because every draw comes from one shared stream in call order, a re-implementation that draws in a different order produces different (equally valid) games; reproducing Pro's exact sequences would need the draw order and the runtime's seeding, neither of which the Lingo exposes. From Q-RND-03.
- **The value-correction pattern is narrow, not a format contract.** The defaults reader pre-sets every value, overwrites each with the file's item and then replaces only five specific bad cases; the scores reader starts at zeros and keeps the conversions of the supplied items. There is no format or version check and no general range check, only those five corrections; what the readers make of any other malformed content is a runtime outcome (`unknown`). From Q-SET-07.

- **A seed might hide in the runtime or the projector.** Possible and out of reach: the claim is scoped to the Lingo, which the search covers completely for this build. The projector's configuration is not the game's code (F002's runtime reading is separate).
- **The sound toggle's default might be off.** Not decodable: nothing initialises it, and what the display frame's comparison does with an unset value is runtime behaviour. The screen task can see it in one launch.

- **Any behaviour across games that needs a save this build lacks.** Replay, scenario exchange and position restore cannot exist here; the registered build's file behaviour is out of scope (rule 19).

- **DOS Isle Wars.** The DOS half of this task's questions is not answered here, and nothing is claimed for it (rule 19).
