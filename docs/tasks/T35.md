- **Easy** (rule 6): a one-row addition to a markdown finding, with a contract test that pins

- **Why**: The rule 18 carve-out permits a model agent to run the original Pro binary under Wine
  on the user's machine, but constraint F names `tools/check_no_originals.py` as the gate, and
  the gate needs a table of known-good hashes to verify against. The F019 finding already pins
  one hash for one set+variant: `iwp-2.0-996e86c5` / `unregistered` /
  `c4d7a248646454adeb48232e3ac7b3d2c0f08b290051a79d6fe6e47bb76b594e`. The table is what
  T36's check reads and what T37's task file references. Without the table, the carve-out is
  permitted but not operational.
- **Evidence**:
  - F019 (`findings/F019-pro-setup-rules.md`): the existing pinning of the binary's sha256 for
    the `iwp-2.0-996e86c5` set, the unregistered variant.
  - `spec/setup.md`: the same sha256, cross-referenced from the static reading's "Sources" line.
  - CLAUDE.md rule 18 carve-out, constraints A and F: the locality rule and the tool-check rule
    that this table supports.
  - `findings/F019-pro-setup-rules.md`'s "What this does not establish" section: the absence
    claims about file handlers and the decompiler's runtime faithfulness — relevant because the
    table is the *named-good* half of a known-bad/known-good gate.
- **Owns**:
  - `findings/F019-pro-setup-rules.md` (modified): a new section "Known-good binary hashes"
    with at least one row: set id, variant, sha256, install path, signed-on date.
  - `formats/known-good-iwp-set.schema.json` (new, optional): a JSON schema for the row, so the
    T36 check can validate the table at CI time. The schema's pattern is the same shape as
    `evidence-manifest-1`'s.
- **Scope**:
  - **Protects:** rule 18 (the table is text in a finding, not a binary, not a copy); rule 20
    (the row's sha256 is reproducible from the F019 finding; re-reads do not change the
    row).
  - The table has at least one row: set id `iwp-2.0-996e86c5`, variant `unregistered`,
    sha256 `c4d7a248646454adeb48232e3ac7b3d2c0f08b290051a79d6fe6e47bb76b594e`, install path
    `/mnt/c/Users/<owner>/Downloads/Isle-Wars-Pro_Win_EN_v20-Shareware/`, signed-on date
    `2026-10-08`.
  - The row's contract is testable: a sample record whose `start_state.sha256` matches the row
    is accepted by the future T36 gate; a record whose hash does not match is refused. The
    test lives in the F019 finding or in `formats/` next to the table, not in `tools/` (the
    gate is T36).
  - Cross-references in `spec/setup.md` are updated to point at the new table, not at the
    in-line sha256. The in-line sha256 stays for the static reading's "Sources" line; the
    table is the canonical source for the gate.
  - **What this does not establish:** the table does not pin a sha256 for any other set+variant.
    Adding a second row (e.g. a registered build, when the owner has one) is a separate task
    and a separate review. The table is the *minimum* the gate needs to be operational; it is
    not a comprehensive set of every Islepro.exe the owner has ever run.
  - **Not in scope:** the gate itself (T36), the T-number task file (T37), the harness copies
    (`docs/process.md`, `TEMPLATE.md`, the `run-task` and `delegate` skills, `harness_imperial`).

- **Hazards**:
  - **Hash transcription**: the sha256 is a 64-char hex string; one dropped or transposed
    character makes the gate refuse every legitimate run. The contract test is the
    defence: a record whose hash is the row's hash must pass; the row's hash is exactly
    what's in F019.
  - **Placeholders left in the row**: the install path and signed-on date must be real, not
    `<owner>` or `<date>`, **except where the project's standing anonymisation convention
    applies** (the install path is the Windows path under the user's account, and the
    repo's convention is to record the path with `<owner>` as the account name; see
    `formats/run-1.schema.json`'s `machine` field for the same convention). The row's
    footnote in F019 must explicitly say the install path uses the standing anonymised
    form and that the gate matches by hash, not by path. The signed-on date is a real
    date, not a placeholder.
  - **A second row added in the same PR**: do not. The second row needs its own task, its own
    review, and its own F019 entry; bolting it onto this PR skips both.
