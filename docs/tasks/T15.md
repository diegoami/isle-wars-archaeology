# T15 Minimal driver: DOS Isle Wars (W5b)

- **Kind**: runtime (a reusable driver over T11's cycle and T14's navigation, a 10-repeat cycle, a
  short finding; no game rule)
- **Issue**: #63 · **Branch**: `task/T15-iw-dos-driver` · **Merge after**: T14 (merged)
- **Implementer**: claude **opus** (`task-agent-heavy`, effort `medium`), worktree isolation, on the
  user's machine (C3: building a driver needs the live game, and OpenCode cannot reach the copy,
  L26). Opus from the start, because a task file must say why (rule 6): T13, the same task for
  Pro, needed Sonnet plus two Opus rework rounds. Its review found the same classes of holes each
  round: process identity, unchecked command results, liveness at stage boundaries, seal
  symmetry, resource ownership.
- **Reviewer**: opencode `gpt-6.1-sol` (GPT-6.1 Sol, effort `low`), another family, after the quota
  check (rule 6). Substitutes: GLM-5.3, then DeepSeek V4 Pro. A Claude reviewer is never allowed.
  Lines marked `[C3]` need the copy or the display, so the main session runs them and posts their
  output on the PR.
- **Hard** (rule 6): a new mechanism across several files (a driver API over the spike), and every
  launch must keep T11's seal. Its failure would let a run be recorded `completed` on a wrong or
  unsealed state.
- **Why**: every DOS experiment after this (T16's crafted saves, T18's determinism, T20–T23's
  rules) needs a driver that reaches a known state, acts, observes and resets the same way every
  time, and fails loudly otherwise. T11 and T14 built a cycle and a step language as a spike, one
  script per run.
- **Evidence**:
  - game-archaeologist 07, W5b: "minimal driver per artifact: launch → known screen → one input →
    before/after observation → terminate/reset, repeated". Its review test: "10× cycle with
    identical before-state hash; kill the game mid-cycle → the driver recovers or fails loudly".
  - F005 (T11): the seal, the run copy, the option box as the known screen at about 17 s, identical
    captures across runs, stop by SIGTERM with `quit warning=false`, and the reset by run-copy diff.
  - F007 (T14): the step language (`navsteps.py`), the board reader, the notice guard, the required
    waits, and the files the game writes (`ISLEWAR.SCR`, `DFT`, `SAV`; R009–R024).
  - T13 (PR #54, parked): the Pro driver and its three reviews. Their findings are the checklist
    for this one. The fix Sol's round 2 pointed to:
    - one liveness guard around every public method and step;
    - one subprocess helper that every command the driver relies on goes through, which checks
      the exit status;
    - a per-invocation marker, with a pidfd re-check before any signal;
    - the second seal check repeating every check of the first;
    - a display the run started itself.
- **Owns**: `runtime/iw-dos/**` (a new `runtime/iw-dos/driver/`, plus changes to
  `runtime/iw-dos/spike/**` only where the driver reuses it); `setup/iw-dos/**`, only to keep the
  seal; `findings/F008-*`; `experiments/E006-iw-dos-driver/**`, `runs/E006/**`, `evidence/E006/**`,
  with probe logs, tables and timings under `experiments/E006-iw-dos-driver/measurements/**`
  (rule 20); the matching tests under `tests/`.
- **Scope**:
  - **Protects:** T11's seal on every launch:
    - the run copy checked with `check --strict` before launch;
    - only `C:` mounted, read-only where the seal says;
    - a private network namespace;
    - alias and bind-mount refusal;
    - `completed` only on a clean finish.

    It also protects the meaning of `completed`: a repeat records it only when it reached its known
    before-state, sent at least one input whose command succeeded, observed, and reset the run copy
    to its baseline.
  - **The driver**, a small API that a later experiment imports, never a new command per run:
    - start a session: the seal, Xvfb, DOSBox-X, launch;
    - wait for a named known screen, by pixels;
    - perform steps in T14's step language;
    - observe: a screenshot by hash, a region, a file the game wrote;
    - terminate and reset.

    Every failure raises a named error, and a repeat that hits one records `aborted: <reason>`. By
    construction, from the start (T13's lesson):
    - one guard checks the game and the display before and after every public method and every step;
    - one helper runs every subprocess and raises on a non-zero exit;
    - signals go only to this invocation's own processes, re-checked through a pidfd;
    - the check immediately before launch repeats every first check that can change.
  - **The cycle**, built on the driver: launch → the option box → one input (Set level) → before and
    after screenshots → terminate → reset, repeated 10 times in one command. Record one `run/1`
    record per repeat, under `runs/E006/`.
  - **Recovery:** kill DOSBox-X mid-cycle, by SIGKILL from outside and by closing its X client. The
    driver records that repeat `aborted`, resets, and the next repeat starts from the baseline. A
    test with a fake game visits this edge, and one `[C3]` run shows it on the real game.
  - **F008** (proposed), short and like F006:
    - the time per repeat (median and range over the 10);
    - the before-hash identity;
    - the recovery result;
    - "What this does not establish".

    Artifact `iw-dos-3.1-30121376`; Experiment E006; tier V2; max intervention I1 (screenshots).
  - **Not in scope:** any game rule; playing a full game; crafted saves (T16); W7b's determinism
    experiment (T18); Pro.

- **Hazards**:
  - **Weakening the seal for speed.** A faster cycle that skips a check is a failure, not a gain.
  - **Fixing call sites one by one.** T13's three rounds came from guards added per call site. Put
    them in one place that every path goes through, and test that structure.
  - **Other sessions' processes** (#32): touch only those this invocation started. Other projects
    run DOSBox-X and Xvfb on this machine.
  - **Clicking an order, upgrade or registration control**: T14's notice guard stays on.
  - **Overwriting a measured output** (rule 20).
